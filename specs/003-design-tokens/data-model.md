# Data Model: Design Tokens Source

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Research**: [research.md](./research.md)

This feature has three kinds of data:

- the two token sources, committed in `packages/tokens`;
- the derived output generated from them;
- what the check builds in memory for one run.

The check writes nothing and keeps nothing between runs. Field names in the check's model are
descriptive, and the code may name them differently.

File paths are relative to the repository root, with `/` as the separator. Lines and columns
count from 1, and columns count UTF-16 code units, as in 002.

## Stored files

### Token export

`packages/tokens/penpot/tokens.json`. The site's tokens exactly as Penpot 2.18.3's Single file
export writes them (FR-001, research R2, R3). The layout is in
[contracts/token-sources.md](./contracts/token-sources.md).

| Part | Notes |
|------|-------|
| Sets | One top-level key per set, its full name as a literal string. Values are trees of groups and tokens |
| `$themes` | Array of themes: `id`, `name`, `group`, `description`, `isSource`, `selectedTokenSets` |
| `$metadata` | `tokenSetOrder`, `activeThemes`, `activeSets` |
| Form | `JSON.stringify(value, null, 2)`, with no trailing newline. Never edited by hand |

### Motion token source

`packages/tokens/motion/tokens.json`. Durations and easing curves, in the same layout (FR-008,
FR-042, FR-043, research R4). It's edited by hand.

### Derived output

Generated by `npm run token-output`, committed, and never edited by hand (FR-005, research R10).

| File | Holds |
|------|-------|
| `packages/tokens/src/tokens.generated.css` | `:root` with every custom property of the active combination, then `@custom-media` rules for breakpoints |
| `packages/tokens/src/tokens.generated.ts` | The description (every name and its type), theme groups, active themes, and every combination's resolved values |

What code may rely on is in [contracts/token-output.md](./contracts/token-output.md).

## Check model

### Location

Where a problem is (FR-035, SC-007): `file`, `line`, `column`. It's `1:1` when there's no
narrower position, as with a missing file.

- **In a token source**:
  - a token's `$value` for problems about its value;
  - its key for problems about its name;
  - the theme object for theme problems;
  - the set's key for set problems.
- **In a site file**: the start of the offending value, property or name.

### SourceRead

The result of reading one token source, using content-check's `readDocument` (research R5).

| Field | Type | Notes |
|-------|------|-------|
| `source` | `export` \| `motion` | |
| `file` | string | The fixed path |
| `state` | `checked` \| `missing` \| `unreadable` | |
| `tree` | `jsonc-parser` node | When readable. Tokens are found by walking it, so repeated keys are seen |
| `problem` | Problem | `missing-file` or `unreadable-file` |

### TokenSet

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | The top-level key, any string |
| `source` | `export` \| `motion` | |
| `order` | integer | Its index in `$metadata.tokenSetOrder` |
| `definitions` | TokenDefinition[] | In source order |

**Rules**:

- Every set must be enabled by at least one theme, or it's `unused-set` (FR-012). An empty set is
  accepted (FR-018).
- `tokenSetOrder` must list every set exactly once and nothing else, or it's
  `unsupported-content`.

### TokenDefinition

One token as written in one set.

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | Key parts joined by `.`. A dotted key contributes its parts as written |
| `set` | TokenSet | |
| `type` | string | `$type` |
| `value` | JSON value | `$value` |
| `description` | string | `$description`, kept exactly, any characters |
| `references` | string[] | Every `{name}` in the value, in composite parts and inside arithmetic too (FR-015) |
| `location` | Location | Of `$value` |

**Rules**:

- **Structure**: a token object has exactly `$value`, `$type` and `$description`. A group holds
  only groups and tokens, with no `$` keys. Anything else is `unsupported-content` (FR-013).
- **Type**:
  - In the export, `$type` is one of the 17 Penpot types (Key Entities). Any other type is
    `unsupported-content`. For `duration` or `cubicBezier`, the detail points to the motion
    source (US1 scenario 5).
  - In the motion source, `$type` is `duration` or `cubicBezier`. A Penpot type there is
    `wrong-source` (FR-042, US5 scenario 2). Any other type is `unsupported-content`.
- **Names**: every part is non-empty and matches `^[A-Za-z0-9_-]+$`, or it's `unusable-name`
  (FR-020).
- **Duplicates**: the same name twice in one set is `duplicate-token`, listing every occurrence
  (FR-016). The same name in both sources is `duplicate-token` too (FR-047).
- **Token used as group**: a name that is a token anywhere and also begins another token's name
  (`a.b` and `a.b.c`), in any set of either source, is `token-used-as-group` (FR-022).

### Theme, ThemeGroup and Combination

| Entity | Fields | Notes |
|--------|--------|-------|
| Theme | `group`, `name`, `id`, `sets` (enabled set names, per source), `sources` | Identity is `group` + `name`. A theme in both sources is one theme (FR-048) |
| ThemeGroup | `name`, `themes`, `active` | Every group in either source |
| Combination | one theme per group | Written `mode/light + motion/standard`, groups in code-unit order. A **full combination** takes one theme from every group in either source. A **source combination** takes one theme from each of one source's own groups |

**Which themes take part**: a theme that is `theme-without-group` or `theme-without-sets` takes
no part in groups, combinations or the active-theme rules, and an `activeThemes` entry naming it
is ignored. It still counts as enabling its sets, so its sets aren't `unused-set` as well. That
way it's reported once, and causes no `theme-mismatch` or `invalid-active-themes` of its own
(FR-023, FR-054). A group exists when at least one of its themes takes part, and a source's own
groups are the groups where it has such a theme.

**Full combinations**: every way to pick one theme from every group, groups and themes in
code-unit order. Each source contributes to a full combination its resolution for the source
combination of its own groups. When one of a source's own groups has no theme with the name the
full combination picks, that source contributes no tokens to it. For example, the motion source's
group `mode` holds only `light` and the full combination has `mode/dark`: every motion name is
then a `theme-mismatch` there (FR-048).

**Rules**:

- The export must have at least one theme. A theme must enable at least one set, or it's
  `theme-without-sets`. An export with no theme at all is `theme-without-sets` on `$themes`
  (FR-004).
- A theme's `group` must not be empty, or it's `theme-without-group` (FR-004).
- A theme must not enable a set its source doesn't contain, or it's `missing-set` (FR-011).
- `activeThemes` must give every group exactly one active theme, and each entry must name a real
  theme. A group in both sources must have the same active theme in both. Anything else is
  `invalid-active-themes`, naming the group and the active themes found (FR-054).
- The **active combination** is the active theme of every group.

### Resolution

Per source, for each source combination (research R6):

1. The enabled sets, in `tokenSetOrder`, are merged. A later set's definition of a name wins
   (FR-017). Two winning candidates with different types are `conflicting-types`.
2. Each winning definition's references are resolved against the merged tokens of the same
   source:
   - a name defined only in the other source is `cross-source-reference` (FR-046);
   - a name defined nowhere is `missing-reference`, listing the combinations where it fails
     (FR-009).
3. Cycles are `reference-loop`, one per cycle across all combinations, listed from the name that
   sorts first and back to it (FR-010).
4. Arithmetic is evaluated (research R7), and the value is checked against its type's rule
   below (FR-014). A token whose value depends on a token already reported gets no problem of
   its own.

The result, for each combination, is a **ResolvedToken** per name:

| Field | Type | Notes |
|-------|------|-------|
| `name` | string | |
| `type` | string | |
| `value` | resolved value | A string, a number, or an object or array for typography, shadow and cubic Bézier |

Then, over every full combination (Theme, ThemeGroup and Combination above), each name must be
present with the same type. Every gap or difference is `theme-mismatch`, naming the full
combinations (FR-023, FR-048).

### Value rules

The value each type must resolve to (FR-014, FR-019, FR-045, research R8). A JSON number is
accepted wherever a numeric string is.

| Type | Accepted |
|------|----------|
| `color` | `#` and 3, 4, 6 or 8 hex digits; `rgb()`, `rgba()`, `hsl()`, `hsla()`; a CSS named color; `rgba(<hex>, <alpha>)` |
| `dimension`, `spacing`, `sizing`, `borderRadius`, `fontSizes`, `rotation` | `^\s*(-?[0-9]+\.?[0-9]*)(px\|%)?\s*$` |
| `borderWidth` | as above, not negative |
| `opacity` | a number from 0 to 1, or a percentage from 0% to 100% |
| `number` | a number with no unit |
| `fontWeights` | `100` … `900` in hundreds, `950`, or a Penpot named weight (TK 624-660), optionally followed by ` italic`, ignoring case |
| `fontFamilies` | an array of non-empty strings, or one comma-separated string |
| `letterSpacing` | a number, optionally with `px` |
| `textCase` | `none`, `uppercase`, `lowercase`, `capitalize` (trimmed, ignoring case) |
| `textDecoration` | `none`, `underline`, `strike-through` (trimmed, ignoring case) |
| `typography` | an object with only `fontFamilies`, `fontSizes`, `fontWeights`, `lineHeights`, `letterSpacing`, `textCase` and `textDecoration`, each valid for its own type. `lineHeights` is a number, a percentage or a `px` length, and needs `fontSizes`. Or a whole-value reference to a typography token |
| `shadow` | an array of objects with `offsetX`, `offsetY`, `blur` (not negative), `spread`, `color` (required) and optional boolean `inset`. Or a whole-value reference to a shadow token |
| `duration` | a number with `ms` or `s`, zero or more. Plain `0` is accepted |
| `cubicBezier` | an array of four numbers, the first and third from 0 to 1. Or a whole-value reference |

A token whose first name part is `breakpoint` must also resolve to a number, optionally with
`px` (research R8, R11).

Unknown keys inside a typography or shadow value are `unsupported-content`, not
`invalid-value`, because Penpot drops them on import.

### Code name

How code reads a token (research R9).

| Name | Code names |
|------|------------|
| any token `n` | `--token-` + `n` lower-cased, with `.` and `_` replaced by `-` |
| typography token `n` | the code names of `n.font-family`, `n.font-size`, `n.font-weight`, `n.font-style`, `n.line-height`, `n.letter-spacing`, `n.text-transform` and `n.text-decoration` |
| breakpoint token `n` | its custom property and a custom media name, both the same text |

**Rules**:

- Two different names with any code name in common are `name-collision`, listing every name
  (FR-021). The check covers every name in both sources, including the typography sub-names.
  So `space.1-5` and `space.1.5` collide (US2 scenario 6).
- The **token namespace** is every custom property or custom media name starting with
  `--token-`, ignoring case (FR-051).

### Description

What code sees (FR-025): every token name from both sources with its type, plus the
typography sub-names and breakpoint names it implies. It carries no source. It's built in memory
from the sources for every run (research R12), and the same function generates
`tokens.generated.ts`.

### SiteFile

A file the literal values search looks at (FR-033, research R13).

| Kind | Extensions | Reader |
|------|------------|--------|
| Style sheet | `.css` | PostCSS for structure, CSSTree for values (R14) |
| Component code | `.ts .tsx .js .jsx .mts .cts .mjs .cjs` | `oxc-parser` (R16) |
| Style format without a reader | `.scss .sass .less .styl .pcss .postcss .html .htm .vue .svelte .astro .mdx` | none, so `unreadable-file` |
| Without styles | any other text file | not read, only counted |

Excluded before any of this:

- everything 002's walk excludes, which already covers the derived output (generated files) and
  `packages/tokens/test/`;
- the token export and the motion token source, `packages/tokens/penpot/tokens.json` and
  `packages/tokens/motion/tokens.json` (FR-033). The package's own code,
  `packages/tokens/src/index.ts`, is site source and is searched like any other;
- image and font files by extension (`.svg .png .jpg .jpeg .gif .webp .avif .ico .bmp .woff
  .woff2 .ttf .otf .eot`).

| `text` | string | As written |

### Check parts

A part whose inputs aren't readable doesn't run, and is listed under "Checks not run"
(FR-034, FR-036).

| Part | Needs | Notes |
|------|-------|-------|
| Export rules | the export | Structure, names, sets, themes, resolution and values within the export |
| Motion rules | the motion source | The same, plus wrong-source and motion values |
| Cross-source rules | both sources | Names in both, collisions, groups, cross-source references, combinations, active themes across sources |
| Derived output | both sources, with no problem from the three parts above | Builds both files in memory and compares |
| Token names in site files | both sources | `unknown-token` against the description |
| Literal values search | nothing | Always runs |

When one source is unreadable, references in the other that would cross into it are reported as
`missing-reference`, because the other source's names aren't known.

### Report

The sorted problems, then the summary (FR-036, FR-037):

- each source's path, state and counts of sets, themes and tokens;
- the derived output's files and state (`current`, `stale`, or `not checked`);
- the number of site files searched for literal values, and of site files without styles;
- the checks not run;
- the number of problems of each type, zeros included;
- the result line.

The exact text is in [contracts/cli.md](./contracts/cli.md).
